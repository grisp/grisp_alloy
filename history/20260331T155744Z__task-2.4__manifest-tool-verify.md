## Objective
Implement `manifest-tool verify` so Alloy manifests can be checked against their embedded integrity section with the documented exit-code split for mismatch, structural failure, and parse failure.

## Investigation Notes
- Task 2.3 already introduced the shared canonicalization and SHA-256 digest
  path used by `manifest-tool hash`.
- Task 2.4 needs to reuse that exact byte-stream generation so verification
  compares against the same canonical form producers write into manifests.
- The workflow-critical behavior for this task is the exit-code split:
  mismatch `1`, structural validation `2`, parse failure `3`.

## Key Decisions
- Implemented `manifest-tool verify` directly in
  `scripts/tools/manifest-tool` so it reuses the existing manifest root
  reader/validator and therefore preserves the established parse (`3`) vs
  structural (`2`) failure split from `validate-root`, `get`, and `hash`.
- Reused the existing `basic_term_canon` + SHA-256 helper path from Task 2.3
  instead of duplicating hashing logic, so `verify` checks the exact canonical
  byte stream written by `hash` and future manifest producers.
- Treated malformed or unsupported integrity metadata (missing section,
  duplicate section, wrong field types, unsupported digest algorithm,
  unsupported canonical form, invalid digest format) as structural failures
  with exit code `2`, leaving exit code `1` solely for true digest mismatch.
- Added a compact summary output (`manifest=... version=... integrity=PASS|FAIL`)
  so successful and failed verifications report the manifest type/version
  alongside the integrity result without dumping raw Erlang terms.

## Unexpected Issues And Resolution
- A nested anonymous-function clause in the first verifier draft missed a
  clause separator, which caused an escript compile-time syntax error during
  focused testing. The implementation was corrected immediately and the full
  manifest-tool suite was rerun to confirm the final parser structure.
