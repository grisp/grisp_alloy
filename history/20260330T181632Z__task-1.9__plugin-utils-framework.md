## Investigation Notes
- `scripts/utils/plugin_utils.sh` does not exist yet.
- There is an older `scripts/plugins/project.sh` implementation that hard-codes project plugin discovery and dispatch; it is useful as behavioral context but does not match the newer generic framework design.
- The design scopes `plugin_utils.sh` as a category-agnostic utility, while higher-level loaders like `scripts/plugins/project.sh` are expected to consume it in later tasks.

## Key Decisions
- Implemented `scripts/utils/plugin_utils.sh` with the documented exported
  surface:
  - `plugin_load`
  - `plugin_call`
  - `plugin_read`
  - `plugin_has`
- Used a category-scoped global array convention `PLUGIN_TYPES_<CATEGORY>` so
  higher-level loaders can iterate deterministically over loaded plugin types
  without adding extra accessor APIs beyond the design contract.
- Kept `plugin_utils.sh` category-agnostic:
  - it only constructs `<category>_<type>_<action>` function names,
  - it does not embed any project-specific detection/build semantics.
- Made plugin load order deterministic by sorting `*.sh` paths before sourcing
  and by recording type names in that same order.
- Made `plugin_read` strict about action success while tolerant about output
  shape:
  - non-zero exit aborts with contextual error and returns the plugin's exit
    code,
  - stdout lines without `=` are ignored,
  - only the first `=` splits key from value so values can still contain `=`.

## Unexpected Issues And Resolution
- The initial load-order implementation used command substitution into an array,
  which worked functionally but triggered a shellcheck warning (`SC2207`).
- Replaced that with `mapfile` over a sorted process substitution so the load
  order stays deterministic without lint suppressions.
