## Objective
Extend `scripts/tools/manifest-tool` with the documented `get` command so it can read a top-level field from any Alloy manifest and print either the plain-string representation or the raw Erlang term.

## Investigation Notes
- Task 2.1 already established the shared manifest root reader/validator and the parse-vs-structural exit split (`3` vs `2`); Task 2.2 should extend that path instead of reparsing manifests separately.
- The `get` contract is intentionally top-level only and must distinguish plain-string output from `--format erlang` output.
- The current manifest-tool does not yet implement any documented public command, so `get` will be the first user-facing verb beyond the Task 2.1 foundation command.

## Key Decisions
- Implemented the documented `get` command in `scripts/tools/manifest-tool`
  instead of adding another task-local helper verb, making this the first
  public manifest-tool command on top of the Task 2.1 reader foundation.
- Added descriptive top-level usage output so `manifest-tool` now reports the
  available commands and examples when invoked with no command or `--help`,
  instead of failing with a terse single-line error.
- Reused the existing manifest root reader/validator for `get` so the command
  inherits the same failure split:
  - exit `3` for parse/read failures,
  - exit `2` for invalid manifest root/structure,
  - exit `1` for a missing field.
- Kept field lookup strictly top-level, matching the design contract. No nested
  path syntax was added.
- Implemented the plain output surface exactly for the value families called
  out in the design:
  - binaries -> plain UTF-8 string,
  - atoms -> atom name,
  - integers -> decimal string,
  - lists of atoms -> space-separated atom names.
- Required `--format erlang` for complex values (for example nested proplists),
  returning a clear exit-2 error instead of guessing at a lossy plain-string
  encoding.

## Residual Risks / Follow-ups
- `manifest-tool get` is limited to top-level field access by design. Any later
  need for deeper manifest traversal should come through a deliberate contract
  change rather than ad-hoc dotted-path parsing.
- Integrity, hashing, and merge behavior remain for Tasks 2.3 through 2.5, so
  `manifest-tool` is still only a partial implementation of the full design.
