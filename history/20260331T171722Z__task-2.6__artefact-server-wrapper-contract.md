# Task 2.6 - artefact-server wrapper contract and final tool relocation

## Objective

Implemented the canonical artefact-server surface used by
`alloy serve artefacts`, including the documented CLI names, validation
behavior, and the final relocation of the authoritative implementation into
`scripts/tools/artefact-server`.

## Initial Investigation

- Current `scripts/commands/serve-artefacts.sh` is still a transitional wrapper
  that blindly execs `/artefact_server`.
- The repository contains a legacy top-level `artefact_server` executable but no
  `scripts/tools/artefact-server` implementation yet.
- No dedicated shell tests currently cover `serve-artefacts.sh` option
  validation or wrapper invocation behavior.

## Key Decisions

- Moved the actual Erlang escript implementation into
  `scripts/tools/artefact-server`, updated
  `scripts/commands/serve-artefacts.sh` to dispatch through it, and removed the
  legacy repository-root `artefact_server` duplicate so the tool path is
  authoritative.
- Updated the relocated escript parser to accept the documented wrapper-facing
  options:
  `--certfile`, `--keyfile`, `--cacertfile`, `--security-pack`,
  `--identity`, `--port`, `--root`, and `--verbose`.
- Added early CLI validation in the tool layer so invalid combinations fail
  before any filesystem or listener setup:
  - `--certfile` and `--keyfile` must be provided together.
  - `--cacertfile` requires manual TLS.
  - `--security-pack` is mutually exclusive with manual TLS files.
  - `--identity` is valid only with `--security-pack`.
- Preserved compatibility aliases (`-S`, `-n`, `--name`) in the Erlang tool so
  the command-facing contract can stabilize without forcing an immediate
  backend rewrite.

## Unexpected Issues

- The first validation pass treated `--cacertfile` as enough to imply manual
  TLS, which let the process fall through to root-directory validation.
  Tightened the manual-TLS detector to require `--certfile` or `--keyfile`
  presence so the intended CLI error is emitted first.

  resolves security-pack TLS material from the existing on-disk layout instead
  of the final documented `secpack capabilities` / `secpack tls` command
  contract. This was left for later command/TLS integration work.
