## Initial Investigation

- The design and current Task 5 backlog already assume a builtin `nuggets/`
  repository staged into `motherlode/builtin/`, but the checkout had no
  `nuggets/` tree at all.
- Smelterl’s current planner fixtures show the minimum nugget set needed for a
  valid plan seed: one each of `builder`, `toolchain`, `platform`, `system`,
  plus a top-level product; the manifest seed additionally requires a
  `target_arch_triplet` export.
- A bootstrap chain based on Buildroot's internal toolchain and a smoke-test
  platform keeps early Task 5 validation cheap and decoupled from the still
  unimplemented real embedded/toolchain nuggets.

## Key Decisions

- Added a real builtin nugget repository instead of an empty placeholder
  registry. An empty `nuggets/` tree would satisfy the staging path contract
  but would still leave `smelterl plan` unable to resolve any top-level
  product, so it would not unblock meaningful Phase 5 validation.
- Used a bootstrap sample chain centered on `toolchain_smoke` and
  `platform_smoke` rather than waiting for the real Crosstool-NG and GRiSP
  nuggets. `toolchain_smoke` uses Buildroot's internal toolchain so the smoke
  build can exercise a real Buildroot configuration without requiring a
  separately produced Alloy SDK toolchain yet.
- Renamed the sample target to the agreed smoke-test naming scheme:
  `platform_smoke`, `system_smoke`, `bootflow_smoke`, and `smoke_product`.
  This makes the whole chain read as a local smoke-test target without
  overloading Alloy's existing `host` terminology.
- Included a `bootflow_smoke` nugget in the bootstrap chain so the sample
  product already satisfies the firmware-variant/bootflow expectations
  embedded in the current Smelterl and design contracts.
- Added a real `builder_buildroot` pre-build hook so the smoke chain can fetch
  and extract the configured Buildroot release into `_build/buildroot` and wire
  the Buildroot download/ccache directories into `_cache/buildroot`.
- Kept the bootstrap nugget content intentionally thin: enough metadata, hook
  behavior, and defconfig fragments to support real plan/generate/build smoke
  runs, without pretending the final embedded builtin nugget set is already
  implemented.
- Captured the manual Buildroot-debugging follow-up in the design and Task 5.8
  planning as a target-local `make_alloy` helper. The helper belongs with the
  per-target Buildroot execution task because it needs the same Alloy
  environment and `O=` / `BR2_EXTERNAL=` values that task will centralize.

## Unexpected Issues And Resolution

- The refined smoke chain moved the platform/toolchain/bootflow dependencies
  under `system_smoke`, but the focused shell test still expected those
  dependencies directly on `smoke_product`. The final test now asserts the
  intended transitive shape: the product selects `builder_buildroot` and
  `system_smoke`; the system owns the smoke platform, toolchain, and bootflow
  backbone.

## Validation Notes

- Added focused shell coverage in `scripts/tests/test_builtin_nuggets.sh` for
  the builtin registry entries, the sample product dependency chain, the
  builder pre-build hook, and the bootstrap toolchain/platform/bootflow
  metadata.
- Verified the new sample chain with direct Smelterl smoke runs:
  - `smelterl plan --product smoke_product ...`
  - `smelterl generate --plan ... --output-external-desc ... --output-config-in ... --output-external-mk ... --output-defconfig ... --output-context ... --output-manifest ...`
- Verified the generated smoke Buildroot context manually with Buildroot
  `main_defconfig` and `make` invocations using target-local `O=`,
  `BR2_EXTERNAL`, and the required `ALLOY_*` environment.

## Design Changes

- Updated `docs/03_ALLOY_DESIGN.md` to make the target-local `make_alloy`
  helper the canonical manual Buildroot debugging path. Plain workspace
  `make` remains Buildroot behavior after configuration, but Alloy should not
  rely on it as the documented interface because generated Kconfig sources and
  hook wrappers need Alloy context variables.

## Residual Risks / Follow-ups

- The bootstrap nuggets unblock staging and planning work, but they are still
  sample validation targets; later tasks still need to implement the real
  embedded builtin nugget set and the real toolchain/bootflow behavior.
- Task 5.2 remains the next Alloy follow-up: it should stage this real
  builtin repository into `motherlode/builtin/` instead of fabricating a
  placeholder builtin source.
- Task 5.8 should generate the documented per-target `make_alloy` helper so
  Buildroot debugging can reuse the exact Alloy environment instead of relying
  on manually reconstructed shell aliases.
