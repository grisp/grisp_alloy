## Investigation Notes
- `scripts/utils/security_utils.sh` does not exist yet.
- The next planned task is tightly scoped to the orchestrator-side helper layer; the hook-facing `security_tools.sh` API is documented separately and remains for a later task.
- The design requires strict path-only security-pack inputs, early validation via `capabilities`, and key validation for `secpack info` / `secpack env` output before the orchestrator exports or persists anything.

## Key Decisions
- Implemented the documented orchestrator-facing security utility surface:
  - `security_resolve_pack`
  - `security_generate_overlay`
  - `security_info`
  - `security_export_env`
  - `security_validate_kv_output`
- Kept `security_resolve_pack` strict about the design's path-only contract:
  bare command names without `/` are rejected even if a same-named executable
  would exist on `PATH`.
- Treated successful `security_info` / `security_export_env` output as a
  filtered stream:
  - blank lines are ignored,
  - non-`key=value` lines are dropped,
  - invalid keys fail fast with the design-defined error message,
  - values may still contain `=`.
- Preserved pack stderr and exit codes for orchestrator-facing subcommands so
  future command handlers can treat exit 2 as capability/no-op where the design
  requires it (`generate-overlay`, `env`) without losing pack diagnostics.
- Kept `security_generate_overlay` caller-owned for directory creation, matching
  the firmware-flow design that the orchestrator prepares the staging directory
  before invoking the pack.

## Unexpected Issues And Resolution
- The first test draft used an `assert_file_exists` helper that is not provided
  by this repository's `bash_unit` setup, which would have made the overlay
  success test a false positive.
- Replaced that assertion with the harness's established `assert_status_code`
  pattern so the overlay file check is real and consistent with the existing
  shell tests.
