# Task 5.3: Smelterl binary management

## Objective

Implement Alloy-side Smelterl executable resolution for `alloy build sdk` so
the command can reliably build or reuse the cached Smelterl escript before the
later plan/generate orchestration tasks invoke it.

## Context

The submodule/bootstrap prerequisite portion of this task was already completed
in earlier migration work. The remaining gap is command-local binary
management: read Smelterl's version, build `smelterl` with `rebar3
escriptize` when no cached artefact exists, rebuild in development mode, and
export the cached executable path for subsequent Phase 5 steps.

## Outcome

`alloy build sdk` now resolves the Smelterl version from
`smelterl/src/smelterl.app.src`, exposes the executable path as
`ALLOY_SMELTERL`, reuses the cached `artefacts/tools/smelterl-<VERSION>`
binary when present, builds it with `rebar3 escriptize` when missing, and
forces `rebar3 clean && rebar3 escriptize` when `ALLOY_DEV_MODE=true`. After
the versioned executable is validated, the command refreshes
`artefacts/tools/smelterl` as a relative symlink to that current version and
exports the symlink path as `ALLOY_SMELTERL_LINK`.

The command still stops after workspace/motherlode setup until the following
Phase 5 plan/generate tasks land, but the Smelterl executable prerequisite is
now satisfied before that handoff point.

## Decisions

- Smelterl checkout presence remains enforced by the top-level `alloy`
  entrypoint for normal command use. The command script also validates the
  checkout directly so focused command tests and direct invocations fail with
  a clear local error.
- Tests provide an explicit cached Smelterl artefact for existing staging
  scenarios so routine shell coverage does not depend on a real `rebar3`
  build.

## Residual Notes

The next task, `Task 5.4`, can consume `ALLOY_SMELTERL` directly for the
`smelterl plan` invocation instead of resolving the executable again. The
stable `ALLOY_SMELTERL_LINK`/`artefacts/tools/smelterl` path is intended for
developer convenience, while orchestration should keep using the versioned
path for traceability.
